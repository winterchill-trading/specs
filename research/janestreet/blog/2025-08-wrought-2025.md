# What the interns have wrought, 2025 edition

- Source: <https://blog.janestreet.com/wrought-2025/>
- Published: 2025-08-27
- Kind: blog post

## Summary

- Annual round-up of intern work, opening with short mentions: optimizing neural-net sequence
  models across compilation toolchains, build priorities in the shared action-execution
  service so low-priority builds do not slow urgent ones, and a CSS LSP whose validator found
  much invalid CSS in existing apps.
- More short mentions: generic optional arguments that can use representations other than
  `option`, and a JIT that makes the Hardcaml simulator competitive with Verilator while
  starting faster.
- One short mention is directly on our turf: a quickcheck-style tool that tests trading
  systems with randomized sequences of market events and shrinking heuristics that reduce
  failures to minimal cases.
- Another adds predicate pushdown to the internal data warehouse, with a small query planner
  that derives narrow key ranges from filter expressions before the full query engine runs.
- JSQL, the firm's own SQL dialect used for filtering tabular data in UIs, tools and
  configuration, gained an index-aware in-memory evaluator: it derives an over-approximate
  key range ("selection") from the WHERE clause and executes it against `Map.t` (range
  queries) or `Hashtbl.t` (point lookups), with heuristics to choose among several indexes.
- On 3.8 million rows the indexed evaluator was about 700x faster for an equality filter and
  about 30x faster for a range filter; much of the effort went into keeping the API simple.
- New ocamltorch bindings use OxCaml's local mode and a `with_rc_scope` function so tensors
  are refcounted and freed deterministically at scope exit, with nested scopes and a
  controlled way to return tensors outward, replacing forced `Gc.full_major` calls.
- Removing those GC calls made other waste visible, such as unnecessary CPU/GPU
  synchronizations.
- A shared-memory library passes pointers to refcounted objects between trading processes
  instead of re-serializing nested data with shared substructure on every message, since
  neither process's GC can manage the shared segment and GC churn is unwelcome anyway.
- It uses modes for safety: atomic compare-and-set on counts, `read_write` visibility only
  during single-owner initialization and `read` for readers, unique handles so copies must go
  through an explicit increment, consuming free and send operations, and local mode on
  release, which amounts to borrow checking; it is being integrated into production.

## Relevance to us

- **Testing and simulation:** randomized market-event sequences with shrinking test a trading
  loop far better than hand-written scenarios, and [mm-core](../../../repos/mm-core.md)'s
  quickcheck tests cover only the pure strategy. **Action:** add a Base_quickcheck generator
  of event sequences (BBO moves, trades, fills) driven through `Live.Make` over the in-memory
  `Venue.S` in `mm-core`, asserting that absolute position never exceeds the risk limit.
- **Data platform:** pushdown only pays when stored data can be skipped; our
  [parquet](../../../repos/parquet.md) writer emits min/max statistics per row group, but
  row groups default to about one million rows, so a one-hour filter rarely skips anything.

  L2 tables with smaller row groups (for example 128k rows) and check with DuckDB

  [oxcaml-claude-skills](../../../repos/oxcaml-claude-skills.md).
